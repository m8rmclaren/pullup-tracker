# Pull-up Tracker v2: iOS

Status: **draft**, revised 2026-10-13. How the native iOS app is laid out, built and
tested. It starts at M3 (see [product.md](product.md#milestones)). From M3, iOS leads the design
and the PWA follows.
Data formats and the API are in [v2-design.md](v2-design.md).

## Decisions at a glance

| Topic | Decision |
|---|---|
| iOS minimum | iOS 18 / watchOS 11, the SDKs in Xcode 16.4 (see Toolchain). |
| iOS logic | `TrackerCore` Swift package, dependency-light, tested on Linux. |
| Local storage | SQLite (via GRDB) in the App Group container, shared by app, widgets and intents. |
| Project file | Generated by XcodeGen from `project.yml`. `.xcodeproj` is not committed. |
| CI | Linux: TS + `TrackerCore`. macOS runner: Xcode build and tests. Xcode Cloud: TestFlight. |

## Architecture

### Layout

```
ios/
  project.yml                 XcodeGen spec: targets, entitlements, App Group, signing team
  TrackerCore/                Swift package — no UIKit/SwiftUI; builds and tests on Linux
    Sources/TrackerCore/      Entry, merge, catalog, definitions, DayCalendar, Stats, Resolver, SyncEngine, APIClient
    Sources/TrackerCoreTesting/  fake server and scheduler, store conformance, for this and TrackerStore's tests
    Tests/TrackerCoreTests/   runs shared fixtures + engine tests with a fake transport
  TrackerStore/               Swift package — the GRDB replica store in the App Group container; macOS only
  App/                        SwiftUI app: screens, composer UI, App Intents, Live Activity, passkey UI
  Widgets/                    WidgetKit: ring, interactive repeat-set, Control Center control
  Watch/                      watchOS app + complications
```

It lives in this repo. An API change and both clients land in one PR, and the fixtures are
shared. The `.xcodeproj` is generated by XcodeGen and git-ignored. A project file is
hostile to merges and can't be checked without Xcode. `project.yml` is readable text any
session can edit.

Everything around the composer call (the resolver, draft expansion, board evaluation) is in
`TrackerCore` and tested there. If the on-device model arrives later, only its call lives in
`App/`, because the framework doesn't exist on Linux.

### TrackerCore

Behavior is pinned by the shared fixtures in [v2-design.md](v2-design.md#shared-fixtures).
`catalog.json` reaches the Swift package as a copied resource. A test fails if the copy
differs from `src/shared/catalog.json`.

- **`Entry`, `Definition`, `pickWinner`, `normalize`, `isValid`**: ports of `model.ts`.
- **`DayCalendar(zone:)`**: days in the user's zone. Only the UTC offset comes from
  `TimeZone`; the calendar arithmetic is done in the package over the proleptic Gregorian
  calendar, so day keys match JavaScript's `Date` exactly. Day keys stay `YYYY-MM-DD`
  strings, as in `time.ts`.
- **`Stats`**: a port of `stats.ts`, extended per exercise and per unit.
- **`Resolver`**: names to ids, and draft expansion.
- **`SyncEngine`** is an actor that ports `tracker.ts`'s semantics: 1.2 s debounce,
  exponential backoff capped at 5 minutes, at most one sync in flight with a queued rerun,
  an outbox entry cleared only if the acknowledged version is still the latest, and the
  cursor reset when the account changes. It depends on `ReplicaStore` (entries,
  definitions, outbox, cursor, account, settings, each mutation transactional) and
  `SyncTransport`. Tests use `MemoryReplicaStore` and a fake server, as
  `test/tracker.test.ts` does.

  Two differences from `tracker.ts`. The engine keeps no copy of the replica: every read and
  write is a store transaction, because another process may have written since. And a
  response that arrives after the token changed is dropped whole, outbox kept, rather than
  merged into the new account's replica.
- **`APIClient`** builds requests, including the `x-amz-content-sha256` payload hash
  CloudFront's origin access control needs. It hashes with CryptoKit on Apple platforms and
  `swift-crypto` on Linux, the package's only dependency.

### Storage across processes

The app, widget extension and App Intents can each write a set, in separate processes. All
use one SQLite database in the App Group container, through GRDB, in WAL mode. Each write
is one transaction: upsert the entry and add it to the outbox.

Any process may run a sync. Two concurrent syncs are safe by construction: pushes are
idempotent merges, the cursor is written as `max(stored, new)`, and outbox rows are cleared
only where the stored `updatedAt` still matches the one sent.

`TrackerStore`'s `SQLiteReplicaStore` stores entries and definitions as their wire JSON,
beside the columns a query needs, so a field added to the model needs no migration. Each
process opens its own `DatabasePool` on the file, with a busy timeout so a writer waits out
another process's transaction instead of failing. The app must post
`Database.suspendNotification` as it goes to the background, or iOS kills it for holding a
lock on a file in the shared container. Every store passes the same conformance check
(`TrackerCoreTesting`), and the sync tests run against SQLite too, including two
connections writing at once.

At about 4,000 sets a year, the whole history loads into memory for stats in milliseconds.
SQLite is there for safe concurrent writes, not for size. SwiftData was rejected: its
multi-process behavior is opaque, it can't be tested on Linux, and it would sit awkwardly
between the CRDT and its own change tracking.

### Sync triggers on iOS

- **A write.** Debounced, inside `beginBackgroundTask`, so a set logged just before the
  phone locks still goes out.
- **Foreground**, and every minute while the app is visible.
- **Widget and intent writes** try a short sync (about 3 s), then leave the rest to the app.
- **`BGAppRefreshTask`** pulls friends' totals opportunistically, to keep widgets fresh.
- **Every write** reloads widget timelines and updates the Live Activity.

### Watch

The Watch is a full sync client with its own session token. The phone requests a device
link and sends the code over WatchConnectivity, and the Watch redeems it. It syncs straight
to the server over Wi-Fi or LTE, with or without the phone. The Watch gets the pad and
Repeat, not the composer.

## Build, test, release

**Cloud sessions run Linux and can't run Xcode.** That shapes the loop:

| Layer | Where it builds and tests | Who verifies |
|---|---|---|
| Server, TS shared code, PWA, fixtures | Linux: `npm run check` | CI and cloud sessions |
| `TrackerCore` | Linux: `swift test` (Swift toolchain in the environment setup script) | CI and cloud sessions |
| App, widgets, Watch (compile + unit tests) | macOS runner: `xcodegen generate && xcodebuild test` | CI, logs readable from a session through GitHub |
| Look, feel, haptics, the passkey ceremony | A device | **You**, from TestFlight, with a short checklist per milestone |

**CI.** `pipeline.yml` runs `TrackerCore`'s `swift test` on Linux. `ios.yml` runs on macOS,
only when `ios/**`, `src/shared/**` or the fixtures change (macOS minutes cost about 10×
Linux): today `TrackerStore`'s tests, and the Xcode project's build and tests once it
exists. PR checks use GitHub Actions, not Xcode Cloud, so a session can read the
logs and fix its own red build.

**Toolchain.** Local builds use Xcode 16.4, with the iOS 18.5 and watchOS 11.5 SDKs: the
operator's Mac stays on a macOS that can't run Xcode 26. So the minimum is iOS 18, and all
code compiles with those SDKs. An iOS 26-only API (Foundation Models, the newer system
design) goes behind `#if compiler(>=6.2)` and `#available(iOS 26, *)`, so it compiles away
locally and turns on in a newer Xcode. Local runs use the iOS 18 Simulator. Builds for a
phone come from Xcode Cloud, which chooses its Xcode version in the cloud. App Store
Connect only accepts builds made with a recent SDK, and Xcode 16.4 may not install to a
phone running a newer iOS than it knows.

**Running it.** From `ios/`, `xcodegen generate` writes `Tracker.xcodeproj`; open it, or
build with `xcodebuild -project Tracker.xcodeproj -scheme Tracker -destination
'platform=iOS Simulator,name=iPhone 16'`. Debug talks to `npm run dev` on
`http://localhost:5173`. Override it with `API_BASE_URL=http://localhost:<port>` on the
`xcodebuild` line when the dev server lands on another port. Sign the Simulator in with the
device link the dev server prints. Passkeys need the real domain's AASA listing the app
(`APPLE_APP_ID` = `CP4PXEQ2P5.com.haydenroszell.tracker` in the repo's Actions variables), so
they work only once that is deployed. The Team ID is `CP4PXEQ2P5`, the bundle id
`com.haydenroszell.tracker`, and the App Group `group.com.haydenroszell.tracker`. They are
generic on purpose: a bundle id can never change once the app is registered, and the product
doesn't have its name yet. The name people see is `CFBundleDisplayName`, which changes freely.

**Release.**
- Xcode Cloud builds and uploads to TestFlight on pushes to `main` that touch `ios/`.
  Signing stays with Apple.
- **TestFlight** while building (M3–M4): a public link, light beta review.
- **The App Store** from M5. Open sign-up and a share-a-link growth loop only work if a
  friend can install from the App Store. TestFlight builds expire after 90 days and cap at
  10,000 testers. App Review will want: account deletion, a privacy label (name, fitness
  data, nothing linked to identity), the third-party-AI consent for Describe, and a
  way to report or block other users' content (see Risks in
  [product.md](product.md#risks)).

## PWA follow-ups

iOS design changes still to carry back to the PWA (see [product.md](product.md#the-pwa)).

- **Trends chart axis.** The y-axis ticks fall on round steps (5, 10, 20, 25, 50, …), and a
  timed exercise's ticks are whole durations (15s, 30s, 1m, 2m, …) labelled as durations.
  The top of the axis is the first tick above the data. The PWA ticks at 0, half and the
  max, as bare numbers.
- **Heatmap.** The selected day's line under the grid opens that day; the PWA's only shows
  it. The first column's month label is left off when the next month starts within two
  weeks, so the labels don't overlap.

## Risks

| Risk | Mitigation |
|---|---|
| The TS and Swift logic drift | Shared fixtures in both suites. A change to merge, time, stats or resolution isn't done until both pass. |
| A session can't see the UI it wrote | Thin views over `TrackerCore`, macOS CI, a per-milestone device checklist. A local session on a Mac can build and screenshot the Simulator; cloud sessions can't. |
| Multi-process SQLite writes | WAL, one transaction per write, an idempotent sync, a two-connection test. |
| Fragment universal links don't open the app | Check on a device in M3. Fallback: a paste field. |
