# Native iOS app: design

Status: **draft**, October 2026. This doc covers the decisions that are expensive to reverse:
data formats, the API, auth, and how the iOS code is laid out and tested. Screens and
interactions are deliberately left loose. They are cheaper to find by using a build than by
specifying them here.

## Summary

The app grows from a pull-up log into a log for any calisthenics movement, and moves from a
PWA to a native iOS app. The AWS backend stays and gets a few additive changes:

- Sets gain an exercise, variations (grip, progression stage, tempo), and a timed-hold form.
- Sign-in becomes **passkeys**, so an account survives any device. Invites still decide who
  can join.
- A leaderboard route reads the per-day totals the backend already maintains.

The iOS client is SwiftUI. Its logic (model, merge, Denver calendar, stats, sync engine)
lives in a plain Swift package that builds and tests on Linux. That lets cloud sessions and
Linux CI verify most of the client without a Mac. The app, widget and Watch layers stay
thin, and are built and tested on a macOS CI runner.

## Goals

1. **Getting data in is as fast as possible.** Repeating the last set is one tap: in the
   app, on a widget, in Control Center, from the Action button, by voice, or on the Watch.
2. **The day reads at a glance.** One ring holds every rep done today, and it shows up on
   the Lock Screen and the Watch too.
3. **Any calisthenics movement fits one input pattern**, including variations and holds.
4. **The login survives anything:** new phone, deleted app, wiped storage.
5. **Friends see each other**, on a leaderboard that costs one query to read.
6. **The existing guarantees hold:** no lost writes, local-first logging, offline works.

## Non-goals (for now)

- Android, and a public App Store release. Friends install through TestFlight.
- Feeds, comments, reactions, and following individual people.
- Workout programs, coaching, rep-difficulty weighting.
- Per-user time zones. Every day is still a Denver day (see Open questions).
- Sign in with Apple. Passkeys meet the stability goal without a third party.

## Decisions at a glance

| Topic | Decision |
|---|---|
| Daily total | Every rep of every rep-based exercise counts 1:1. Holds are tracked in seconds, separately. |
| Exercises | A fixed catalog shipped with the app. The server validates the format, not membership. |
| Variations | Flat list of ids. Each belongs to one group (grip, progression, tempo, …), at most one per group. |
| Old data | A set with no `exerciseId` is a pull-up. No migration. |
| Old clients | `/api/sync` requires `protocolVersion: 2`. Older clients get 426 until they update. |
| Auth | Passkeys (discoverable credentials) on the app's custom domain. Session tokens unchanged. |
| Joining | Invite-only, as today. Redeeming an invite ends with creating a passkey. |
| Friends | Everyone on the deployment is one group. |
| Goal | Moves from per-device to the profile, so the leaderboard can show progress toward it. |
| iOS minimum | iOS 26 / watchOS 26. |
| iOS logic | `PullupCore` Swift package, dependency-light, tested on Linux. |
| Local storage | SQLite (via GRDB) in the App Group container, shared by app, widgets and intents. |
| Project file | Generated by XcodeGen from `project.yml`. `.xcodeproj` is not committed. |
| CI | Linux: TS + `PullupCore`. macOS runner: Xcode build and tests. Xcode Cloud: TestFlight. |
| PWA | Gets the v2 model in M0 and passkeys in M1, then freezes once the native app reaches parity. |

## 1. Product shape

Directional, not a spec.

**Today screen.** The ring holds today's reps across all exercises. Holds show as a second,
smaller figure ("2:40 held"). Below the ring is the **set card**: the exercise, variations
and added weight the next set will be logged as. It is prefilled from your last set, so most
of the time you don't touch it. Below that is the pad:

- **Tapping a number logs a set** with the set card's context. This is the same one-tap
  model as today.
- **The pad adapts to the exercise.** It shows the six counts around your usual count for
  that exercise and variation, not a fixed 3–8. A pad built for pull-ups is useless for
  push-ups.
- **Recent combos** sit as chips above the card ("Pull-up · wide", "Front lever · tuck ·
  hold"). One tap switches context. This is the set builder: the next set is assembled
  from your history, not from menus.
- **A hold exercise turns the pad into a timer**: one big start/stop button, plus quick
  durations for holds you forgot to time.
- **Undo, haptics and the double-tap guard** carry over from the PWA.

The order you sketched (reps, then exercise, then variation, then log) is four taps for
every set. Making exercise and variation sticky context makes the common case one tap and a
change two. The rest of the order follows from that.

**Added weight** stays sticky per exercise for the day and resets to bodyweight the next
day, as it does today.

**Stats.** These are today's stats, per exercise or across all of them: streaks,
completed-day averages, week-to-date, best day, heaviest set. Charts use Swift Charts.

**Leaderboard.** Today, this week and this month. Two rankings: total reps, and % of your
own goal. The second is the fair one between people at different levels. There is a
per-exercise filter.

## 2. Data model v2

### Entry

```json
{
  "id": "9f2c…", "doneAt": 1791489600000, "updatedAt": 1791489600000,
  "exerciseId": "pull-up", "variationIds": ["wide-grip"],
  "reps": 6, "addedWeightLbs": 25
}
```

| Field | Rule |
|---|---|
| `exerciseId` | Slug, `^[a-z0-9-]{1,40}$`. Absent means `pull-up`. Normalization drops it when it equals `pull-up`, so old and new pull-ups have one shape. |
| `variationIds` | Slugs, at most 6, unique, stored **sorted**. Absent or empty means none. Normalization drops an empty list. |
| `reps` | Integer 1–1000 (`MAX_REPS` rises from 100; push-ups and squats run high). |
| `holdSeconds` | Integer 1–3600. Exactly one of `reps` and `holdSeconds` is present. |
| `addedWeightLbs` | Unchanged. Allowed on holds too (a weighted hang). |

Sorting `variationIds` matters. `["tuck","negative"]` and `["negative","tuck"]` must be the
same version, or `sameVersion` sees a change that isn't one.

**Tiebreak.** `pickWinner` must stay a total order. After `updatedAt` and `deleted`, it
compares, in order: `reps ?? 0`, `holdSeconds ?? 0`, `addedWeightLbs ?? 0`,
`exerciseId ?? "pull-up"`, `variationIds` joined with `,` (empty when absent), then `doneAt`. Old entries carry none of
the new fields, so their outcomes don't change. The same chain is implemented in Swift and
checked against shared fixtures (§5).

### Catalog

`src/shared/catalog.json` is the single source for exercises and variations:

```json
{
  "exercises": [
    { "id": "pull-up", "name": "Pull-up", "measure": "reps", "category": "pull", "variationGroups": ["grip", "tempo", "assistance"] },
    { "id": "front-lever", "name": "Front lever", "measure": "hold", "category": "skill", "variationGroups": ["progression"] }
  ],
  "variations": [
    { "id": "wide-grip", "name": "Wide grip", "group": "grip" },
    { "id": "tuck", "name": "Tuck", "group": "progression" },
    { "id": "negative", "name": "Negative", "group": "tempo" }
  ]
}
```

The first catalog would include:

- **Pull:** pull-up, chin-up, muscle-up, inverted row.
- **Push:** push-up, dip, pike push-up, handstand push-up.
- **Legs:** squat, pistol squat, lunge.
- **Core:** hanging leg raise, toes-to-bar.
- **Holds:** dead hang, plank, hollow hold, L-sit, handstand, front lever, back lever, planche.

Variation groups: grip, progression (tuck → advanced tuck → one-leg → straddle → full),
tempo (negative, pause, explosive), assistance (band, feet-assisted), and form (archer,
one-arm).

The server checks slug format only. A new catalog entry then ships in an app build with no
backend deploy. A client that meets an id it doesn't know shows it title-cased.

Custom exercises are later work. They would be ids prefixed `custom-`, with names stored on
the profile.

### Day total

The day total is still recomputed from entries on every change. It gains a per-exercise
breakdown, so one month query still answers every leaderboard:

```json
{
  "day": "2026-10-08", "reps": 61, "sets": 11, "bestSetReps": 12, "holdSeconds": 95,
  "byExercise": {
    "pull-up": { "reps": 31, "sets": 6, "bestSetReps": 8 },
    "push-up": { "reps": 30, "sets": 3, "bestSetReps": 12 },
    "plank": { "sets": 2, "holdSeconds": 95, "bestHoldSeconds": 60 }
  },
  "version": 7
}
```

`reps` keeps its meaning of "the number on the ring", now across all rep-based exercises.
A day total written before v2 has no `byExercise`, and readers treat it as entirely
`pull-up`. A retried push or any later edit rewrites it anyway, so no backfill is needed.

### Profile

The profile item `U#<userId> P` gains `dailyGoalReps` and `goalUpdatedAt`, merged
last-writer-wins. The goal stops being per-device. The phone, Watch and widgets have to
agree on it, and the leaderboard needs it for "% of goal".

### New items

| pk | sk | item |
|---|---|---|
| `U#<userId>` | `K#<credentialId>` | passkey: public key (COSE), sign count, transports, createdAt, label |
| `C#<digest>` | `C` | pending WebAuthn challenge: purpose, userId?, expiresAt, ttlEpochSeconds |

Neither item needs a new index. Passkey login finds the credential through the `userHandle`
the authenticator returns, which is the user id, so the key is known. Challenges are looked
up by digest, like invites. `test/dynamodb.test.ts`'s `CreateTableCommand` doesn't change.

## 3. API

Every change is additive except the protocol gate.

**Protocol gate.** `/api/sync` requires `protocolVersion: 2` in the body. Without it the
server returns 426 *Update the app*.

The gate prevents a quiet data loss. A v1 client's `normalizeEntry` strips fields it doesn't
know. If a v1 client received a chin-up and later edited it, its edit would win under
last-writer-wins and turn the chin-up back into a pull-up. With the gate, a stale PWA sees
426 once, and the service worker loads the new code on its next launch. Future breaking
additions bump the version the same way. TestFlight builds can show "Update required".

**`POST /api/sync`.**
- Request: `{ protocolVersion, pushedEntries, sinceCursor }`, with entries in the v2 shape.
- Response: unchanged, except `account` gains `dailyGoalReps` and `goalUpdatedAt`.

**`POST /api/profile`** (authenticated)
- Request: `{ dailyGoalReps, goalUpdatedAt }`.
- Last-writer-wins on `goalUpdatedAt`. Returns the stored profile.

**`POST /api/leaderboard`** (authenticated)
- Request: `{ fromDay, toDay }`, at most 62 days.
- Response: `{ users: [{ id, name, dailyGoalReps, days: [DayTotal] }] }`.
- Implementation: one or two queries on the `by-month` GSI, plus a batch get of profiles.
- The server returns raw day totals and the client ranks them. Periods, filters and "% of
  goal" are then client decisions, and a widget can compute "you're #2 today" from the same
  response.
- A user with no sets in the range doesn't appear.

**Passkeys** (§4):
- `POST /api/passkey/register/options` (authenticated) → creation options.
- `POST /api/passkey/register` (authenticated) `{ credential, label }` → `{ ok }`.
- `POST /api/passkey/login/options` → request options, with no `allowCredentials`
  (discoverable).
- `POST /api/passkey/login` `{ credential, label }` → `{ token, account }`.

**`POST /api/account/delete`** (authenticated) deletes the whole `U#<userId>` partition.
App Store guidelines require in-app account deletion wherever an account can be created.
TestFlight beta review may check it too. Once the profile is gone, the existing check in
`sync` already answers 401, so leftover `T#` token items grant nothing. They can be tidied
up with TTL.

Each new storage operation goes on `Db` and is implemented in both `MemoryDb` and `DynamoDb`,
per CLAUDE.md.

## 4. Auth: passkeys

**Why passkeys.** A passkey belongs to the domain and syncs through iCloud Keychain. A new
phone, a reinstalled app or wiped storage all sign back in with Face ID, with no invite and
no device link. The same passkey works in the native app (through Associated Domains) and
in Safari, so the PWA gets it nearly free. That makes M1 a cheap way to prove the ceremony
before any Swift exists.

**Flows.**

- **Joining.** Open a friend invite and pick a name. `/api/join` creates the account and
  returns a session token, as today. The app then immediately runs passkey registration.
  If you skip or cancel it, the account works on that device and the app keeps prompting
  until a passkey exists.
- **Signing in anywhere.** Tap **Sign in**, then Face ID. The system offers your
  discoverable passkey for the domain, and `/api/passkey/login` mints a new session token
  for this device. There is no username field.
- **Sessions.** The existing `T#<digest>` device tokens are reused as session tokens,
  unchanged. Revocation (`invite.sh revoke`) works as before. `revoke` should also delete
  the user's `K#` items, or a revoked person could sign straight back in.
- **Recovery.** Someone who loses every Apple device *and* their iCloud Keychain uses a
  device link from `invite.sh device`, as today. Once in, they register a new passkey.

**Challenges.** Challenges are 32 random bytes, stored as `C#<sha256>` with a 5-minute
expiry. They are consumed with a conditional delete, like invites, so one can't be replayed.

**Verification.** Uses `@simplewebauthn/server`. Attestation is not required (`none`).
Signature verification isn't something to hand-roll, and that library is the maintained
standard for Node. The Lambda bundle grows modestly.

**The domain is the anchor.** The relying-party id is the app's custom domain. Every
passkey is bound to it, so **choose the final domain before anyone registers a passkey**.
Changing it later strands every credential. This makes the custom domain (already supported
in `infra/`) a requirement, not an option. A `*.cloudfront.net` name can change if the
distribution is recreated.

**Associated Domains.**
- The site serves `/.well-known/apple-app-site-association` with
  `webcredentials.apps: ["<TeamID>.<bundleId>"]` and `applinks` entries for invite links.
- It must be `application/json`, served with no redirect, from the site bucket.
  `publish-site.sh` uploads it with the right content type.
- The app declares `webcredentials:<domain>` and `applinks:<domain>`.

**Invite links in the app.** Links stay `https://<domain>/#join=<code>`. The code rides in
the fragment, so it never reaches CloudFront logs. AASA `components` can match a fragment
(`"#": "join=*"`), so tapping the link opens the app. Verify this early on a device. If it
doesn't hold, the fallback is a "Paste invite" field in the app.

**Not Sign in with Apple.** It needs a Services ID, private key and JWT verification on the
server, and it would add an identity the account has to link to. Passkeys are not
third-party login, so the App Store rule that would otherwise require Sign in with Apple
doesn't apply. It can be added later as a second credential type.

## 5. iOS architecture

### Layout

```
ios/
  project.yml                 XcodeGen spec: targets, entitlements, App Group, signing team
  PullupCore/                 Swift package — no UIKit/SwiftUI; builds and tests on Linux
    Sources/PullupCore/       Entry, merge, catalog, DenverCalendar, Stats, SyncEngine, APIClient
    Tests/PullupCoreTests/    runs shared fixtures + engine tests with a fake transport
  App/                        SwiftUI app: screens, App Intents, Live Activity, passkey UI
  Widgets/                    WidgetKit: ring, interactive repeat-set, Control Center control
  Watch/                      watchOS app + complications
  Shared/                     GRDB store and App Group plumbing used by App, Widgets, Watch
```

It lives in this repo, not a new one. An API change and both clients land in one PR, and
the fixtures are shared. The `.xcodeproj` is generated by XcodeGen and git-ignored. A
project file is hostile to merges, can't be checked without Xcode, and `project.yml` is
readable text that any session can edit.

### Two implementations, one behavior

Merge rules, Denver day keys and stats now exist in TypeScript (the server, and the PWA
while it lives) and in Swift. To stop them drifting, behavior is pinned by **shared JSON
fixtures** in `test/fixtures/`, and both test suites run every case:

- **`merge.json`**: pairs of versions and the expected winner, including every tiebreak
  step and v1 → v2 shapes.
- **`days.json`**: instants and their Denver day key, covering both DST transitions, the
  UTC-midnight crossover, and month and year edges. Wall-clock → instant cases too.
- **`validation.json`**: valid and invalid entries.
- **`stats.json`**: an entry history, a "now", and the expected stats.

The TS suites already contain most of these cases inline. M0 lifts them into fixtures.

`catalog.json` reaches the Swift package as a copied resource. A CI step fails if the copy
differs from `src/shared/catalog.json`. SwiftPM resources can't point outside the package.

### PullupCore

- **`Entry`, `pickWinner`, `normalize`, `isValid`**: a direct port of `model.ts`.
- **`DenverCalendar`** uses `TimeZone(identifier: "America/Denver")` with a Gregorian
  `Calendar`. Day keys stay `YYYY-MM-DD` strings with pure calendar arithmetic, as in
  `time.ts`.
- **`Stats`**: a port of `stats.ts`, extended per exercise.
- **`SyncEngine`** is an actor that ports `tracker.ts`'s semantics: 1.2 s debounce,
  exponential backoff capped at 5 minutes, at most one sync in flight with a queued rerun,
  an outbox entry cleared only if the acknowledged version is still the latest, and the
  cursor reset when the account changes. It depends on two protocols:
  - `ReplicaStore`: entries, outbox, cursor, account, settings, each mutation transactional.
  - `Transport`.

  Tests use in-memory implementations, as `test/tracker.test.ts` does.
- **`APIClient`** builds requests, including the `x-amz-content-sha256` payload hash
  CloudFront's origin access control needs. It hashes with `swift-crypto`, which is
  CryptoKit's API and also builds on Linux. That is the package's only dependency.

### Storage across processes

The app, widget extension and App Intents can each write a set, and they may run in
separate processes. All of them use one SQLite database in the App Group container,
through GRDB, in WAL mode. Each write is a single transaction: upsert the entry and add it
to the outbox.

Any process may run a sync. Two concurrent syncs are safe by construction:

- Pushes are idempotent merges.
- The cursor is written as `max(stored, new)`.
- Outbox rows are cleared only where the stored `updatedAt` still matches the one that was
  sent.

The protocol's idempotence, which already makes retries safe, is what makes multiple
processes safe too.

At about 4,000 sets a year, the whole history loads into memory for stats in milliseconds.
SQLite is there for safe concurrent writes, not for size.

SwiftData was considered and rejected. Its multi-process behavior is opaque, it can't be
tested on Linux, and it would sit awkwardly between the CRDT and its own change tracking.

### Sync triggers on iOS

- **A write.** Debounced, inside `beginBackgroundTask`, so a set logged just before the
  phone is locked still goes out.
- **Foreground**, and every minute while the app is visible.
- **Widget and intent writes** try a short sync, with a time budget of about 3 s, then
  leave the rest to the app.
- **`BGAppRefreshTask`** pulls friends' totals opportunistically, to keep widgets fresh.
- **Every write** calls `WidgetCenter.reloadAllTimelines()` and updates the Live Activity.

### Watch

The Watch is a full sync client with its own session token. It doesn't sign in with a
passkey. The phone requests a device link (`POST /api/invite {kind:"device"}`) and sends the
code over WatchConnectivity, and the Watch redeems it. That reuses existing, tested
machinery. The Watch then syncs straight to the server over its own Wi-Fi or LTE, with the
phone absent or not. It has its own small store. Merging makes the two devices converge.

## 7. Build, test, release

**Cloud sessions run Linux and can't run Xcode.** That shapes the loop:

| Layer | Where it builds and tests | Who verifies |
|---|---|---|
| Server, TS shared code, fixtures | Linux: `npm run check` | CI and cloud sessions |
| `PullupCore` | Linux: `swift test`, needs the Swift toolchain in the environment setup script | CI and cloud sessions |
| App, widgets, Watch (compile + unit tests) | macOS runner: `xcodegen generate && xcodebuild test` | CI. Logs are readable from a session through GitHub. |
| Look, feel, haptics, widgets on a real Lock Screen, the passkey ceremony | A device | **You**, from TestFlight, with a short checklist per milestone |

**CI.**
- `pipeline.yml` gains a Linux `swift test` step.
- A separate macOS job builds and tests the Xcode project. It runs only when `ios/**` or
  the fixtures change, because macOS runner minutes cost about 10× Linux minutes on a
  private repo.
- PR checks use GitHub Actions, not Xcode Cloud, so their logs are readable through the
  GitHub tools a session has. That is what lets a session fix its own red build.

**Release.**
- Xcode Cloud builds and uploads to TestFlight on pushes to `main` that touch `ios/`. It's
  included with the developer membership (25 compute hours a month), and signing stays with
  Apple. No certificates or App Store Connect keys go into GitHub.
- Friends join as **external testers** through a public TestFlight link. The first build of
  each version goes through a light beta review.
- Onboarding a friend has two steps: install the app from the TestFlight link, then tap the
  invite link. The web page at the invite link explains both and links to TestFlight. It is
  the clunkiest part until an App Store release.

**You'll need to provide:**
- Apple Developer Program membership ($99 a year).
- A bundle id, e.g. `com.<you>.pullups`, and an App Group, e.g. `group.com.<you>.pullups`.
- The final domain.
- Associated Domains and App Groups enabled for the app id.
- Swift added to this environment's setup script, so sessions can run `swift test`.

## 8. Milestones

Each milestone ends in something you can use.

**M0: model v2 and leaderboard backend.** Server and PWA only.
- Shared fixtures extracted, and `catalog.json`.
- The v2 entry: `exerciseId`, `variationIds`, `holdSeconds`, `MAX_REPS` 1000, the new
  tiebreak.
- Day totals with `byExercise`.
- The protocol gate, with the PWA sending v2. The PWA shows exercise names on chips but
  gets no new input UI.
- The goal on the profile, and `/api/profile`.
- `/api/leaderboard`.

*Done when:* `npm run check` and the DynamoDB suite are green and deployed. The PWA still
works and old data reads the same.

**M1: passkeys.**
- Challenge and credential storage, the four routes, and `revoke` deleting passkeys.
- The AASA file, and the custom domain made required.
- PWA: register a passkey in Settings, and **Sign in with passkey** on a fresh browser.

*Done when:* you can wipe Safari's data, sign back in with Face ID, and keep your history.
This proves the ceremony and the domain before any Swift exists.

**M2: iOS skeleton at PWA parity for pull-ups.**
- `PullupCore` with every fixture passing on Linux.
- An XcodeGen project and the GRDB store.
- Passkey sign-in and invite join.
- Today screen with ring, pad, undo, edit and delete. A basic Trends screen. Settings.
- macOS CI and Xcode Cloud wired up.

*Done when:* TestFlight build 1 replaces the PWA on your phone for a week.

**M3: every movement.**
- The set card, recent combos, the exercise and variation pickers.
- The adaptive pad and the hold timer.
- Per-exercise stats with Swift Charts.
- App Intents and Shortcuts.
- **The PWA freezes here.**

*Done when:* a mixed session (pull-ups, dips, a front-lever hold) logs with no more than one
extra tap per exercise change.

**M4: leaderboard and friends.**
- The board screen: periods, the two rankings, the exercise filter.
- Invite from the share sheet. Universal-link join.
- Account deletion.

*Done when:* two friends are on TestFlight and on the board.

**M5: logging without opening the app.**
- The interactive widgets.
- The Control Center control and Action button.
- The Live Activity rest and hold timer.

**M6: Apple Watch.**
- The app, Double Tap repeat, complications.
- Pairing through a device link.

**Later:** push notifications when a friend passes you, reminders, HealthKit, planned sets
(queue a ladder so each tap advances it), custom exercises, Sign in with Apple, and retiring
the PWA.

M0 and M1 are pure server and PWA work that can run in cloud sessions start to finish.
M2 onwards needs the Apple account and your device for each milestone's checklist.

## 9. Risks

| Risk | Mitigation |
|---|---|
| The TS and Swift logic drift apart | Shared fixtures run in both suites. A change to merge, time or stats isn't done until both pass. |
| A session can't see the UI it wrote | Keep views thin over `PullupCore`. Use macOS CI for compile and unit tests. A per-milestone device checklist for you. Screenshots from the simulator in CI can be added if needed. |
| Multi-process SQLite writes | WAL mode, one transaction per write, and an idempotent sync. A test with two `ReplicaStore` connections writing at once. |
| Passkeys bound to the wrong domain | Fix the domain in M1, before any registration. Prove it with the PWA. |
| Fragment universal links don't open the app | Check on a device in M2. Fallback: a paste field. |
| TestFlight friction for friends | A two-step invite page. Consider an App Store release (possibly unlisted) once M4 lands. |
| A stale client strips v2 fields | The protocol gate (§3). |

## 10. Alternatives considered

- **CloudKit instead of AWS.** Free and native, but cross-user queries for a leaderboard are
  awkward in CloudKit's public database. It would also discard a working, tested backend
  that keeps web access possible.
- **Game Center leaderboards.** It has a friend graph and recurring leaderboards built in.
  But the data and UI aren't ours, per-exercise boards and "% of goal" don't fit, and every
  friend would need a Game Center account. It could mirror the board later.
- **React Native or Capacitor around the PWA.** These keep one codebase, but widgets,
  Control Center, Live Activities and the Watch all need native targets anyway. The wrapper
  would carry the cost without the payoff.
- **Weighting exercises by difficulty for the daily total.** Fairer, but every weight is
  arbitrary and the ring stops meaning "reps I did". Ranking by "% of goal" handles fairness
  between people instead.

## 11. Open questions

Each has a default the plan assumes. Override any of them.

1. **Denver for everyone?** Default: yes. A shared day keeps "today" on the board the same
   day for everyone. Per-user zones would make each person's day correct, at the cost of a
   board whose days don't line up. Revisit if a friend lives far from Mountain time.
2. **Do holds ever count toward the ring?** Default: no. Seconds and reps don't add.
3. **Does the PWA stay for Android friends?** Default: frozen at M3, still able to sync. It
   is retired when nobody uses it.
4. **Units?** Default: stored in lb, with a display preference for kg (storage step 0.5 lb).
5. **Default leaderboard ranking?** Default: total reps today, with "% of goal" one tap away.
